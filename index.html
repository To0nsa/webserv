Webserv

[](LICENSE)

‍A lightweight HTTP/1.1 server written in modern C++20, compliant with the Hive/42 webserv project specifications.

Webserv is our first large-scale C++ project at Hive/42. The goal was to implement a lightweight, fully working HTTP/1.1 server from scratch, trying to use modern C++ standard libraries.

The server is designed to be RFC-compliant (following HTTP/1.1 [RFC 7230–7235]) and supports essential features such as:

  • Parsing and validating configuration files (Nginx-style syntax).
  • Handling GET, POST, DELETE with static files, autoindex, and uploads.
  • Executing CGI scripts securely with proper environment and timeouts.
  • Multiplexing sockets and CGI pipes in a single poll-based event loop.
  • Graceful error handling, timeouts, and connection reuse (keep-alive).

For reference and correctness, Nginx was used as a behavioral benchmark: routing, error responses, and edge cases were compared against it to ensure realistic and compliant behavior.

This project was both a challenge in systems programming and a solid introduction to networking, concurrency, and protocol design in modern C++.

Core of Webserv

Component Responsibility
**Server** Represents a virtual host configuration. Manages binding (host + port), server names, error pages, body size limits, and a collection of Location blocks.
**Location** Encapsulates route-specific configuration. Defines path matching, allowed HTTP methods, root directories, index files, redirects, CGI interpreters, and upload stores.
**runWebserv** Orchestrates the execution of the web server: initializes Server objects from the parsed configuration, launches sockets, and enters the event loop.

Program Entrypoint

  1. Parse CLI arguments or fallback to default configuration.
  2. Load and normalize configuration (via config parser).
  3. Validate Server and Location objects.
  4. Call **runWebserv()** to start the server runtime.

The program is designed so that configuration and validation are complete before runtime begins, ensuring that only consistent and safe server objects are passed to the execution loop.

1. Tokenization

  • Component: Tokenizer
  • Goal: Convert raw configuration text into a structured list of tokens.
  • Steps:
    • Skip UTF‑8 BOM if present.
    • Ignore whitespace, line breaks, and comments (# ...).
    • Classify tokens into categories:
      • Keywords: server, location, listen, host, root, index, autoindex, methods, upload_store, return, error_page, client_max_body_size, cgi_extension.
      • Identifiers: Alphanumeric strings with -, ., /, : allowed.
      • Numbers & Units: Digits with optional single‑letter suffix (k, m, g).
      • Strings: Quoted values (single ‘’or double"<tt>). * **Symbols:**</tt>{<tt>,</tt>}<tt>,</tt>;<tt>,</tt>,`. * Detect and reject invalid characters, control characters, or malformed identifiers. <h2>2. Parsing</h2> * <strong>Component:</strong> <tt>ConfigParser</tt> * <strong>Goal:</strong> Transform token stream into structured objects (<tt>Config</tt>, <tt>Server</tt>, <tt>Location</tt>). * <strong>Rules:</strong> * <strong>Block structure:</strong> Curly braces <tt>{ ... }</tt> delimit <tt>server</tt> and <tt>location</tt> blocks. * <strong>Directives:</strong> Each directive must end with <tt>;</tt> unless it opens a block. * <strong>Directive placement:</strong> Certain directives are only valid at specific levels: * Server level: <tt>listen</tt>, <tt>host</tt>, <tt>server_name</tt>, <tt>error_page</tt>, <tt>client_max_body_size</tt>. * Location level: <tt>root</tt>, <tt>index</tt>, <tt>autoindex</tt>, <tt>methods</tt>, <tt>upload_store</tt>, <tt>return</tt>, <tt>cgi_extension</tt>, <tt>cgi_interpreter</tt>. * <strong>Nesting:</strong> Locations may not contain other <tt>server</tt> blocks. <h2>3. Configuration Objects</h2> * <strong>Server:</strong> Represents a virtual host. * Holds host, port, server names, error pages, body size limits, and <tt>Location</tt> blocks. * <strong>Location:</strong> Defines behavior for a URI path prefix. * Includes root directory, index file(s), autoindex flag, allowed methods, redirects, CGI settings, and upload store. <h2>4. Normalization</h2> * After parsing, the configuration is <strong>normalized</strong> to ensure consistency and defaults: * Missing <tt>client_max_body_size</tt> → default = <strong>1 MB</strong>. * Missing <tt>error_page</tt> → add defaults for common errors (403, 404, 500, 502 → <tt>/error.html</tt>). * Missing <tt>methods</tt> → defaults to <strong>GET, POST, DELETE</strong>. * Locations without <tt>root</tt> → fallback to <tt>/var/www</tt> (unless redirected). * Root location (<tt>/</tt>) without <tt>index</tt> → defaults to <strong>index.html</strong>. * Normalization guarantees that later validation and runtime logic operate on a <strong>complete and uniform</strong> model. <h2>5. Validation</h2> * <strong>Component:</strong> <tt>validateConfig</tt> * <strong>Goal:</strong> Enforce semantic correctness beyond syntax. * <strong>Checks applied:</strong> * <strong>Presence checks:</strong> At least one <tt>location</tt> per <tt>server</tt>. * <strong>Path rules:</strong> Location paths must start with <tt>/</tt> and not contain segments beginning with <tt>.</tt>. * <strong>Defaults:</strong> Each location must define either a <tt>root</tt> or <tt>return</tt> (but not both with CGI). * <strong>Server names:</strong> Must be unique per host\:port, valid per RFC 1035 (no spaces, no control chars, no empty labels). * <strong>Ports:</strong> Only one unnamed default server per host\:port pair. * <strong>Error pages:</strong> Codes restricted to 400–599. * <strong>Redirects:</strong> Only 301, 302, 303, 307, 308 allowed. * <strong>Methods:</strong> Only <tt>GET</tt>, <tt>POST</tt>, <tt>DELETE</tt> permitted. * <strong>Client body size:</strong> Must be > 0. * <strong>CGI:</strong> Extensions must start with a dot, interpreters must map 1‑to‑1 with declared extensions. * <strong>Roots & Upload stores:</strong> Must exist and be directories. * <strong>Index:</strong> Requires a valid <tt>root</tt>. <h2>6. Error Handling</h2> * <strong>Tokenizer:</strong> Throws <tt>TokenizerError</tt> with line/column context when encountering invalid tokens. * <strong>Parser:</strong> Throws <tt>ConfigParseError</tt> on invalid structure or misplaced directives. * <strong>Validator:</strong> Throws <tt>ValidationError</tt> with descriptive guidance on fixing invalid configurations. </details> <hr> <h1>Networking <tt>SocketManager</tt></h1> The heart of Webserv’s I/O: a single <tt>poll()</tt> loop multiplexing <strong>listening sockets</strong>, <strong>client sockets</strong>, and <strong>CGI pipes</strong>, with strict timeouts and robust error recovery. <details> <summary><strong>See Details</strong></summary> * <strong>Listening sockets</strong>: set up <tt>bind()</tt>/<tt>listen()</tt> for each configured host\:port. * <strong>Event loop</strong>: run non-blocking <tt>poll()</tt> to monitor all descriptors. * <strong>Connections</strong>: * <strong>New connections</strong> → <tt>accept()</tt> → initialize per-client state. * <strong>Reads</strong> → receive → parse (supports pipelining) → route. * <strong>CGI</strong> → spawn, monitor pipes, enforce timeouts, finalize. * <strong>Writes</strong> → stream raw or file-backed responses with keep-alive and backpressure. * <strong>Timeouts</strong>: enforce idle, header, body, and send deadlines. * <strong>Errors</strong>: generate accurate HTTP error responses, close cleanly. </details> <hr> <h1>HTTP Handling</h1> This section explains how <strong>Webserv</strong> processes HTTP/1.1 requests end‑to‑end, from bytes on a socket to fully formed responses, and how the server enforces protocol rules, timeouts, and connection reuse. <details> <summary><strong>See Details</strong></summary> <h2>Request Lifecycle (High‑Level)</h2> 1. <strong>Accept & Read</strong> <tt>SocketManager</tt> accepts client connections on non‑blocking sockets and collects incoming bytes. It * Sets <tt>Content-Type</tt> (MIME by extension), <tt>Content-Length</tt> or <tt>Transfer-Encoding: chunked</tt>, <tt>Connection</tt> (keep‑alive vs close), and error pages. * Streams file bodies (sendfile/read+write) with backpressure; can fall back to buffered I/O for CGI and dynamic content. 6. <strong>Send & Reuse</strong> <tt>SocketManager</tt> writes the response, respecting <strong>write timeouts</strong> and TCP backpressure. If <tt>Connection: keep-alive</tt> and protocol rules allow, the connection stays open for subsequent pipelined requests. <h2>Static Files & Autoindex</h2> * <strong>Static files</strong>: Path is resolved from <tt>root</tt> + URI, protecting against traversal. If an <strong>index</strong> is configured and exists for a directory, it is served. * <strong>Autoindex</strong>: When enabled and no index present, <tt>generateAutoindex</tt> renders a minimal HTML directory listing. * <strong>ETag/Last‑Modified</strong> *(optional)*: If enabled, responses include validators; otherwise strong caching is avoided. Enforces <strong>hard timeouts</strong> (startup, read, total runtime). Build & Test Instructions

Build with Makefile

make
./bin/webserv <path-to-config.conf>

‍The default goal is all. The binary is produced at bin/webserv.

Available Makefile Targets

Command Description
make Build the project in release mode (C++20, -O3 -flto -DNDEBUG -march=native).
make re Clean everything and rebuild from scratch.

make install_test_deps Create a local Python venv in .venv/ and install requirements-test.txt.

Notes

  • Ensure python3-venv and clang-format are installed on your system.
